# iPhone 有货后的购买辅助可行性

调研日期：2026-10-21。范围：中国大陆 Apple 在线商店，个人购买 iPhone 并到店取货。本次只阅读公开官方资料，没有登录、加购、提交订单或付款；以下流程事实来自官方帮助，技术可行性判断不代表已完成实单验证。项目此前没有调研文档目录，记录放在 `docs/research/`。

## 结论

可以继续做“购买辅助”：发现有货后展示具体商品及门店，由用户进入官网完成结账。自动选择门店、填写信息可能有技术实现空间，但需独立验证，不应承诺可以稳定自动下单或保证抢到库存。完全无人值守购买并非现有库存查询功能的简单延伸。

本次在 Apple Developer 公开文档和 Apple 在线商店帮助中，**未找到向普通第三方应用开放、用于中国大陆实体 iPhone 零售订单创建及取货预订的官方 API**。这不是证明所有合作渠道都不存在接口。搜索中常见的 App Store Server API 管理的是 App 内购买交易，不适用于购买实体 iPhone。[官方 API 说明](https://developer.apple.com/documentation/appstoreserverapi)

## 已核实的流程与边界

| 事实 | 对本项目的意义 |
| --- | --- |
| 官网结账包含购物袋核对、账户登录、付款和发票信息、最终下单；订单接受还取决于全额付款。 | 看到“有货”、进入购物袋、产生订单号、付款成功和可取货是不同状态。不能把库存命中当作购买成功。 |
| 到店取货需要在结账中选择取货及门店；部分商品支持取货时段。取货联系人姓名须与购买人和证件一致；需等到取货通知再到店，携带订单号和有效证件。 | 除 SKU 外，还需要用户选择门店、联系人，以及可能的时段。App 不能代替用户实际到店及身份核验。 |
| 桌面微信支付要求用户扫描二维码；支付宝会转到支付宝网站完成付款；可用方式以结账页为准。 | 不宜设计为后台静默完成支付。 |
| Apple Pay 的线上付款有用户确认步骤，且中国大陆网页使用有额外设备和浏览器限制。 | 不应把其他市场 Mac 的支付体验直接当作大陆桌面端可用能力。 |

来源：[购物体验](https://www.apple.com.cn/cn/shop/help/shopping_experience)、[Apple 取货服务](https://www.apple.com.cn/shop/help/shipping_delivery)、[付款与安全性](https://www.apple.com.cn/cn/shop/help/payments)、[Apple Pay 购物及地区限制](https://support.apple.com/zh-cn/102626)。

官网帮助未提供可依赖的“加购即锁库存”保证，也未在本次所读页面明确取货库存的锁定时点、未付款保留时间及并发规则。不要据此宣传“自动占库存”。

## 实现路线比较（工程判断）

| 路线 | 可做的内容 | 代价与限制 |
| --- | --- | --- |
| 官方商品页面跳转，用户完成购买 | 有货提示中显示机型、颜色、容量、门店；进入对应官方商品页面；保留门店信息供核对。 | 最适合第一版。仍需验证链接落地后的规格选择；没有公开依据保证 URL 能预选取货门店。 |
| 用户启动的浏览器辅助 | 在可见官网流程中辅助选择商品、取货门店或填写非支付信息，交给用户核对及提交。 | 尚未验证。需要处理页面变化、会话失效、验证码、取货时段变化；自动点击同样不能被视为获得 Apple 的自动化许可。 |
| 仿造网站内部请求直接创建订单 | 理论上研究网站订单请求可能形成自定义客户端。 | 不推荐。缺少公开稳定接口契约；会话、安全令牌和风控行为均未验证。请求超时后的重复下单风险也显著高于只读查询。 |
| 完全无人值守下单付款 | 期望库存命中后直接产生已付款订单。 | 当前证据不足以支持可靠承诺；支付认证及账号验证可能需要用户到场，维护与交易风险高。 |

项目现有商品跳转和门店编号可以复用，但浏览器购物会话、购物袋、结账和订单状态属于新的能力边界。现有库存查询返回成功不意味着具有创建订单权限。

## 网站条款是实际约束

Apple 网站条款限制使用自动程序抓取或监控网站内容、规避导航取得未有意提供的信息，并禁止破坏安全验证、造成不合理高负载等行为。因此，能通过浏览器执行某一步不等于 Apple 允许第三方自动执行；也不应以绕过验证码、身份验证或风控作为方案前提。现有目录抓取和库存轮询的公开发布同样需要考虑该条款，而非仅自动下单需要考虑。[Apple 网站使用条款](https://www.apple.com.cn/legal/internet-services/terms/site.html)

## 推荐下一步

先做可单独验收的“去购买”辅助：通知和任务中给出确切规格与可取货门店，用户点击进入官方购买页；在确认规格、门店和取货流程后再评估浏览器辅助。用户确认购买内容和付款继续留在官网。

后续若要进一步验证，应另行确认研究范围和可接受的交易步骤；优先验证商品链接是否准确落地、登录态是否沿用、取货门店能否由官方支持的方式预选。遇到登录、安全验证和支付确认由用户处理。不得把失败后的无条件重试用于提交订单，应先确认是否已经产生订单，以免重复购买。

未验证：登录态及 Cookie 行为、当前实际结账 UI、门店预选参数、库存保留机制、真实支付兼容性、风控触发条件、订单结果对账方式。本次没有修改 App 源码或执行真实交易。

## 浏览器实测：2026-10-21

经用户授权，在现有 Arc 浏览器会话内验证，不提交订单、不付款。

- 从 App 现有任务选取 iPhone 18 Pro 256GB 银色，SKU `MJT84CH/A`，目标城市上海。
- 打开 `https://www.apple.com.cn/shop/product/mjt84ch/a` 后，官网跳转至 `/shop/buy-iphone/iphone-18-pro/mjt84ch/a`；页面标题和商品摘要均确认完整规格，不必逐项选择机型、颜色和容量。
- 官网供货情况窗口列出上海门店。选中当时显示“今天可取货”的 Apple 香港广场并点击“继续”后，商品页显示该门店。
- 现有购物袋已经有同一规格商品、数量 1；本次没有重复加购，也没有更改数量。购物袋中取货预览同步显示 Apple 香港广场。
- 点击购物袋“结账”后进入 Apple 账户登录／访客结账页。因此，仅能确认沿用了浏览器购物袋及门店偏好，**不能确认已有账户认证状态在结账时仍有效**。未读取或导出 Cookie、令牌或密码。
- 用户自行完成登录并确认后，同一 Arc 会话进入 `/shop/checkout?_s=Fulfillment-init`，可继续操作取货选项；无需向 App 提供或导出账户凭据。这只能证明本次人工登录后能继续流程，不能证明登录态长期有效或以后无需重新认证。
- 进入结账时“我要取货”已选中，但地区是另一城市，未直接沿用商品页的上海门店。将结账地区改为上海黄浦区后，Apple 香港广场显示“今天可取货”，且店铺卡片有蓝色选中边框。
- 已用可见页面核实门店下方商品为 `iPhone 18 Pro 256GB 银色`，与目标 SKU 对应规格一致。页面额外要求取货日期及签到时段；未替用户选择具体时段，也未点击“继续填写取货详情”。
- 最终停在已选香港广场的取货选项页面。没有提交订单、付款、填写取货人信息、新增加购或修改数量。门店偏好和本次结账地区已改变；原有购物袋同规格商品数量仍为 1。
- 实测结论：现有浏览器中的界面操作可以完成规格定位与结账阶段有货门店选择，但必须在结账页重新核对地区、规格、门店与时段。商品页门店预览不能替代结账核对；本次未验证 App 自动执行能力、跨重启会话持续性或官方门店预选 URL 参数。
